# 3sD-INPAINTegration offline security: controls and limits

## Trust domains

Development on GitHub, acquisition on a dedicated connected machine, and
creation on a separate disconnected machine are distinct operations. This PR
is not deployment. Physically disable/disconnect network interfaces on creation
hardware and protect local storage/accounts. Do not place personal images,
embeddings, prompts, generated media, device details or private audit evidence
in Git history, CI artifacts or issue comments.

The offline entrypoints are [verify](../offline/verify_offline.py),
[build](../offline/build_offline.py), [install](../offline/install_offline.py)
and [launch](../offline/launch_offline.py). They share
[common.py](../offline/common.py) and a strict [policy](../offline/policy.json).
Use the commands in [INSTALL](INSTALL.md); running an adapter directly bypasses
these wrappers and is not equivalent.

## Enforced local policy

`offline/policy.json` requires the reviewed flat policy:
`offline_required: true`, `policy_version: 1`, all remote-loading/network/
telemetry permissions disabled and mandatory local-wheel installation gates.
Do not add a nested `linux-unshare` JSON key: Linux namespace enforcement belongs
to the implementation, not an invented policy schema. Unknown/malformed fields
and duplicate JSON keys fail closed. Do not edit this file to permit acquisition.
Required true gates are `install_from_local_wheels_only`,
`verify_artifact_hashes`, `require_pinned_dependencies`, and
`require_verified_network_isolation`. Required false permissions are
`acquisition_on_creation_device`, `allow_remote_dependency_references`,
`allow_runtime_downloads`, `allow_remote_model_code`, `allow_cloud_inference`,
`allow_telemetry`, `allow_crash_uploads`, `allow_update_checks`,
`allow_public_share_links`, and `allow_external_ui_assets`.
`unsupported_platform_action` is `"refuse"`, `missing_asset_action` is `"fail"`,
and `logs` is `"local_only"`. The local roots are `model_root: "models"`,
`work_root: "work"`, and `output_root: "out"`.
The policy expresses requirements; JSON alone does not enforce them. Even a
comment saying “Enforced by launcher” is not a guarantee without the reviewed
launcher/worker actually executing its checks.

Explicit acquisition requires `--acquisition-only --connected-machine
--policy /absolute/separate/acquisition-policy.json`; that separately reviewed
policy must contain `offline_required: false` and `acquisition_only: true`.
These are different schemas/purposes, not interchangeable policy toggles.
Acquisition flags express operator intent; they do not prove which physical
machine is connected or disconnected.

Local runtime/model/wheel paths must be relative POSIX paths within the selected
bundle. Traversal, absolute mapped paths, Windows drive paths and symlink paths
are rejected. `--root` itself is the explicitly selected trusted bundle root.
Operate on trusted storage with no concurrent adversarial writers; these path
checks are not a race-proof filesystem sandbox.

## Integrity and provenance

Supply a human-authenticated local `offline/artifacts.sha256` before offline
operations. Each record is lowercase SHA-256, two spaces, then a unique relative
path. The manifest cannot hash itself. Every listed artifact is checked, and
required files must have matching records. A manifest generated from arbitrary
downloaded files only records their bytes: authenticate it independently through
reviewed provenance and an out-of-band signature/hash channel. Do not treat a
hash next to an untrusted file as proof of origin.

The shared `models/manifest.json` contains metadata, not weights. Required `blocked` entries,
unknown SHA-256, absent local files, unreviewed licenses, absent local config
mappings or mismatched sizes block verification. Resolve model destinations
beneath the configured model root and authenticate every extracted archive
member individually; never hash a directory as if it were the acquired archive.
Current offline verification blocks archive-only ready records and requires
individual ready member records with no extraction; configured directories must
contain only files covered by those records and authenticated artifact hashes.
Source builds additionally
require a ready lock entry with an approved 40-hex commit and license, a clean
local checkout, no unsupported submodules/symlinks, and hashed source files.
Unresolved `null` source revisions must remain blocked until provenance review.

Acquisition validates expected hash/size **before** transferring an asset,
checks bytes afterward, and stages before publication. Reviewed extraction
allowlists and size limits reject traversal, links, special files, duplicate or
unexpected archive members.
Archive acquisition also requires `extraction.member_sha256` with exactly the
allowlisted member keys and trusted hashes before transfer; each extracted
member is checked against it. Deployment still requires individually ready
member records rather than an archive-only ready entry.
HTTPS and bounded retries do not establish a model
license or make a checkpoint safe to execute; hashes must come from a trusted
authority, not an invented prior conversation.

## Installation and execution

Build/install require explicit target requirements and local wheelhouses.
Requirements are exact `name==version --hash=sha256:HASH` records, matched to
trusted wheels; URLs, source distributions, directives and implicit resolver
downloads are rejected. Pip is invoked with `--isolated --no-index
--require-hashes --only-binary=:all: --no-deps --no-cache-dir` and a local
`--find-links`. List every transitive dependency explicitly. Compatible wheels,
Python ABI, native libraries and GPU drivers remain the deployment team's
responsibility.
The isolated installer/build also runs `pip check`; omitted or incompatible
transitive dependencies cause failure rather than being fetched or ignored.

Builds snapshot trusted inputs into local staging and apply reviewed deterministic
patches before explicit recipe argument arrays. Missing recipes/requirements are
blockers; selecting `--target` does not implement an entire CUDA/macOS/Windows
stack. Build output is not automatically trusted: review, hash and transfer it
through the same supply-chain gate before installation.

Build, install and launch execute under a Linux user/network namespace
(`unshare --user --map-root-user --net`). The internal worker verifies its
network namespace differs from the parent's, that only loopback exists, external
IPv4/IPv6 connections are unreachable and external DNS resolution fails.
Failure of namespace creation, probes or child commands blocks execution;
there is no online or “best effort” fallback. Disabled user namespaces on CI/
managed hosts are an expected blocker, not permission to weaken the policy.
The probes are deliberate attempts inside isolation; no successful external
connection or DNS resolution is acceptable.

The worker passes a restricted environment and offline/telemetry flags
(`HF_HUB_OFFLINE`, `TRANSFORMERS_OFFLINE`, `HF_DATASETS_OFFLINE`,
`HF_HUB_DISABLE_TELEMETRY`, `DO_NOT_TRACK`, `WANDB_DISABLED`, `WANDB_MODE`,
`PIP_NO_INDEX`, `PIP_DISABLE_PIP_VERSION_CHECK`). Launch maps model caches to
the local model directory and runs only an explicitly selected, hash-verified,
executable adapter relative to the script's fixed `runtime/` root; it does not accept a shell
command. Environment flags are defense in depth, not the network security
boundary.
The `unshare` subprocess itself also receives the sanitized environment;
inherited `LD_PRELOAD`, `PYTHONPATH`, proxies and secrets are not passed through.

Compatible-host verification may inspect metadata on macOS M1 or Windows;
build/install/launch refuse those platforms because no reviewed isolation
backend exists. Linux x86-64 targets still need functioning namespace support.
Cross-building and a full platform implementation are not claimed.

## Residual risks and diagnostics

A network namespace isolates only the launched processes' network stack; it is
**not** a complete hostile-code sandbox. Filesystem access, inherited descriptors
or OS capabilities, local Unix sockets/IPC, privileged helpers, kernel
vulnerabilities and native/GPU code need separate review. Malicious native
installation hooks could use an inherited communication descriptor or, when
privileges/namespace handles permit, reenter the host namespace. The wrappers do
not isolate the filesystem or authenticate the running interpreter/kernel.
Only trusted, reviewed wheels, sources and adapters belong inside this boundary;
do not use a machine with untrusted privileged services. Physical disconnection
and reviewed process/container/VM isolation remain necessary deployment controls.

`verify_offline.py` hashes local files and checks metadata only; it does not
assert execution isolation, load models, install packages, validate CUDA or
prove a complete creation pipeline. Successful namespace launch means the
selected process completed, not that models, outputs, identity fidelity or
licenses passed acceptance.

Offline failures return nonzero (normally status 2 with `Blocked:`); inspect
the missing-input/policy/hash/host/isolation gate, never retry by enabling the
network. Audit records remain local and contain action, target and outcome,
not personal inputs. They are not signed, tamper-proof or a comprehensive
forensic log; early failures may precede an audit record.
The audit file is restricted to mode 0600 and its parent directory to 0700;
permissions reduce local exposure but do not authenticate log contents.
Child stdout/stderr
are captured rather than automatically uploaded; sanitized stage-specific
diagnostics should be collected locally by reviewed adapters.

Use [the cold-start checklist](INSTALL.md#cold-start-acceptance) and existing
offline tests. A test fixture, mocked probe or environment-variable assertion
is not proof of physical air-gap security. Human review is required for any
policy/isolation change, native dependency, runtime recipe, license decision or
new platform backend. Never automatically merge security changes.
